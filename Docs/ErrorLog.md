# Distributed Job Scheduler — Error & Debugging Log

This log tracks the major errors encountered during the development lifecycle, their root causes, and the exact resolutions applied.

| Date | Component | Error Message / Symptom | Root Cause | Resolution |
| :--- | :--- | :--- | :--- | :--- |
| **Setup Phase** | PostgreSQL Container | `FATAL: password authentication failed for user "jobqueue"` | Port `5432` collision on the host system. The local database intercepted Spring Boot's connection instead of the Docker container. | Changed Docker compose port mapping to `5435:5432` and updated Spring Boot `datasource.url` configurations across all services. |
| **Compilation Phase** | Root Maven Build | `Fatal error compiling: error: release version 21 not supported` | The `<java.version>` property in the POM was set to 21, but the host environment runs OpenJDK 17. | Downgraded `<java.version>` to `17` in the root `pom.xml`. |
| **Compilation Phase** | `submission-service` | `cannot find symbol: method startVirtualThread` | `IdempotencyGuard.java` utilized Virtual Threads, which were introduced in Java 21, violating the Java 17 environment constraint. | Refactored the code to use traditional `new Thread(() -> {...}).start()`. |
| **Dependency Resolution** | Maven Reactor | `Could not resolve dependencies: com.jobqueue:shared-kernel:jar:0.0.1-SNAPSHOT` | The microservices were attempting to inherit `${project.version}` for the kernel, which mapped to `0.0.1`, while the kernel was published as `1.0.0`. | Hardcoded the `shared-kernel` dependency version to `1.0.0-SNAPSHOT` in both microservice POMs. |
| **Testing Phase** | `shared-kernel` | `package org.junit.jupiter.api does not exist` | Missing test dependencies in the module's POM file. | Added `junit-jupiter` and `assertj-core` scoped as `test` to `shared-kernel/pom.xml`. |
| **Compilation Phase** | `submission-service` | `cannot find symbol: class Priority / JobStatus` | `JobRepositoryImpl.java` attempted to map result sets using domain enums but lacked the required imports. | Manually added `import com.jobqueue.shared.model.Priority` and `JobStatus` to the repository implementation. |
| **Compilation Phase** | `worker-service` | `cannot find symbol: class RedisQueueClient` | `QueuePoller.java` attempted to invoke `RedisQueueClient`, which belongs strictly to the `submission-service` package and domain. | Pruned incomplete advanced stubs temporarily to stabilize the build. Cross-service class sharing requires architectural re-evaluation. |
| **Testing Phase** | `submission-service` | `BadSqlGrammarException / PSQLException: Can't infer the SQL type to use for an instance of java.time.Instant` | The underlying JDBC driver cannot automatically map `Instant` to Postgres `TIMESTAMP WITH TIME ZONE` via `JdbcClient.param()` without explicit type markers. | Cast `job.getCreatedAt()` and `job.getUpdatedAt()` explicitly to `java.sql.Timestamp.from()` in `JobRepositoryImpl.java`. |
| **Runtime Phase** | Root `jobqueue-system` | `Unable to find a suitable main class` when running `mvn spring-boot:run` from the multi-module root directory | The root POM is `packaging=pom` — a container module with no main class. The `spring-boot-maven-plugin` in the root POM (version `3.2.5`) was attempting to `spring-boot:run` the parent, which is architecturally invalid. | Removed the plugin from root POM. Added `<skip>false</skip>` only to the executable child modules (`submission-service`, `worker-service`). The correct invocation is `mvn spring-boot:run -pl submission-service` or running each service from its own directory. |
| **POM Architecture** | All modules | Inconsistent Spring Boot versions (`3.2.5` in root, `3.5.14` in child modules) | Child modules (`submission-service`, `worker-service`) pointed directly to `spring-boot-starter-parent` instead of inheriting from the root `jobqueue-system` POM. This broke the multi-module reactor pattern entirely. | Unified all modules under Spring Boot `3.3.5`. Child modules now correctly declare `<parent>` as `com.jobqueue:jobqueue-system:1.0.0-SNAPSHOT`. Removed duplicate Spring Cloud `<dependencyManagement>` blocks from child modules. |
| **Test Logic** | `shared-kernel` | `BackoffCalculatorTest.shouldApplyJitterToRetryTime` — `Expecting actual: 2026-05-03T10:45:29.286Z to be after or equal to 2026-05-03T10:45:29.345Z` | Full-jitter backoff (`ThreadLocalRandom.nextLong(cappedDelay)`) is intentionally random in `[0, cappedDelay)`. The test incorrectly asserted `retry2 >= retry1`, assuming monotonic ordering — impossible with full jitter. | Rewrote test to assert each retry time falls within `[now, now + maxPossibleDelay)` per attempt. Monotonic ordering is now explicitly documented as not a guarantee of this algorithm. |
| **Test Logic** | `submission-service` | `JobTest.shouldNotAllowInvalidTransition` throws `IllegalStateException` at line 34 before the `assertThatThrownBy` block | The test called `job.transitionTo(JobStatus.COMPLETED)` directly in the test body (not inside the assertion lambda), so the exception propagated and crashed the test rather than being caught. | Moved the invalid transition call inside the `assertThatThrownBy(() -> ...)` lambda and added `hasMessageContaining("Cannot transition")` to validate the message. |
| **Test Reliability** | `submission-service` | `JobRepositoryIntegrationTest` fails with `IllegalStateException: Could not find a valid Docker environment` when Docker Desktop is not running | `@Testcontainers` without `disabledWithoutDocker = true` throws a fatal error rather than skipping gracefully when Docker is unavailable. | Changed annotation to `@Testcontainers(disabledWithoutDocker = true)`. Test now **skips** with a warning instead of failing the build when Docker is not running. |
| **Runtime Phase** | All services | `Web server failed to start. Port 8081/8082 was already in use` when starting a service | A previous `mvn spring-boot:run` or `./start-all.sh` background process was still holding the port. Re-running a new instance against the same port collides. | Updated `start-all.sh` to call `lsof -ti:<port> \| xargs kill -9` before launching new instances. Old PIDs are cleared automatically every time the script runs. |
| **Runtime Phase** | All services | `WARN: Unable to start LiveReload server` | Spring DevTools tries to bind a LiveReload server on port `35729`. When two services or two runs compete for the same port, the second fails with a WARN and can block startup. | Disabled LiveReload in both `application.yaml` files via `spring.devtools.livereload.enabled: false`. The `start-all.sh` also explicitly kills port `35729` before launch. |
| **Compilation Phase** | `worker-service` | `cannot find symbol: method ofVirtual()` in `QueuePoller.java` | `Thread.ofVirtual()` and `Executors.newThreadPerTaskExecutor()` are Java 21 APIs. The project targets Java 17. | Replaced with `Executors.newCachedThreadPool()` using a daemon thread factory. Added a comment noting the upgrade path to virtual threads when moving to Java 21. |
| **Smoke Test** | Swagger UI check | `smoke-test.sh` reported FAIL for `/swagger-ui.html` — expected 200, got 302 | SpringDoc redirects `/swagger-ui.html` → `/swagger-ui/index.html`. The `curl` invocation without `-L` does not follow redirects and sees the 302. | Changed the Swagger UI curl invocations to use `curl -s -L` to follow the redirect. All 16 smoke test checks now pass. |
| **Smoke Test** | `smoke-test.sh` | Script exited after first test with `exit code 1` despite correct test logic | `set -e` combined with bash arithmetic `((PASS++))` exits the script when the expression evaluates to 0 (falsy). On the first test the counter was 0 and the script terminated. | Added `set +e` after `set -euo pipefail`, and replaced `((PASS++))` / `((FAIL++))` with `PASS=$((PASS+1))` / `FAIL=$((FAIL+1))`. |
| **Runtime Logic** | `submission-service` | `OutboxPoller` threw SQL exceptions during `SELECT` and `INSERT` | The generated SQL in `OutboxPoller` used `aggregate_type` which was not present in the Flyway schema `V2__create_outbox_table.sql`. Instead, `V2` defined `event_id`. | Updated `OutboxPoller.java` and `OutboxEvent.java` to match the exact `V2` schema, replacing `aggregate_type` with `event_id` and generating a random UUID. |
| **Architecture** | `submission-service` | Outbox records were not written atomically with the job | `JobSubmissionService.submit()` did not call `OutboxPoller.writeEvent()`, and even if it did, the method lacked a `@Transactional` annotation to bind both JDBC operations to one transaction. | Injected `OutboxPoller` into `JobSubmissionService`, added the `writeEvent` call after saving the job, and annotated `submit()` with `@Transactional`. |
| **Metrics Logic** | `worker-service` | Failed job metric emission recorded `jobId` instead of `jobType` in Prometheus tags | `JobExecutor` catch block passed `jobId` directly to `metricsService.recordJobCompletion`, creating extremely high-cardinality tags (one unique tag per job execution). | Wrapped a safe DB fetch in a try-catch to resolve the `jobType` from the `jobId` and passed `jobType` to the metrics recorder instead. |
